# Changelog

## [Unreleased]
- A call with a guessed parameter name now gets a hint. When exactly one required argument is missing and exactly one argument was not recognized, the error ends with `did you mean "deviceId" instead of "hostId"?`. With several missing or several unrecognized arguments the pairing is ambiguous, so no hint is given.
- Guard against an alert's `resourceId` being used as a device ID. It is the deviceDataSourceId, but the `resourceId` alias now lets it through to the write tools, where it could hit an unrelated device. `delete_resource`, `update_resource`, `update_resource_property` and `delete_resource_property` now warn about it in the `deviceId` description, and the delete and property write results include `target` (`deviceId` and `displayName`) so a wrong target is visible.
- More argument aliases, each seen in real failed calls: `hostId` for `deviceId`, `datasourceId` for `dataSourceId` and `group_id` for `groupId` (the canonical name wins if both are given, and a tool that declares the alias itself is untouched). Ambiguous names (`id` on tools with several IDs, `name`, `dataSourceId` vs `deviceDataSourceId`) are deliberately not aliased.
- Checking an Active Discovery run. `schedule_resource_discovery` returns an empty acknowledgement and the instance tools show only counts, so "not run yet", "finished with no instances" and "failed" looked the same. New knowledge resource `lm://knowledge/active-discovery-status` documents the collector debug commands that answer it (`!adlist h=<host> ds=<DataSource>` for each run's status WAITING/EXECUTING/DONE/FAILED/EMPTY, time and error message; `!adetail <task id>` for the detail), how to read them against `scheduledAt` (a request runs every DataSource on the resource one after another, so a row can take a minute or two), and the schedule -> check -> `list_resource_instances` workflow. Linked from the `schedule_resource_discovery` and `execute_debug_command` descriptions.
- Config version history. New read-only `list_resource_configs` (the collected versions of a ConfigSource instance on a resource, newest first: id, version, pollTimestamp, configStatus, changeStatus, comparedWith; no config text by default) and `get_resource_config` (one version with its config text and the diff against the version it was compared with, cut to `maxChars` 40,000 / `maxDiffLines` 500 with a `truncationNote`). `list_resource_configs` also returns `collection`, which answers "how long since this resource collected the config?": `status` `never` (no instance, or one that never collected), `ok`, or `overdue` (no collection for more than twice the ConfigSource's collection interval), with `lastCollectedTime`, `secondsSinceCollected` and a summary, from the instance's `lastCollectedTime` (a version's `pollTimestamp` is only when the config last changed). Pass `deviceId` and `configSourceId` and the instance is looked up; a resource without one reports `never` instead of an error. This lets you read an earlier version of a config and tell a ConfigSource that is not collecting from one that is.
- Time-of-day alert thresholds without hand-writing `alertExpr`. `create_datasource`, `update_datasource` (per datapoint) and `update_resource_group_datasource_thresholds` (per `dpConfig` entry) accept `alertThresholds` (`[{window:{start,end}, operator, warn, error, critical}]`) and `timezone`, validate them (HH:mm, operator, positional levels, IANA zone) and build the string, for example `( 06:30 22:30 ) = 1 2 3 , ( 00:00 01:30 ) < 3 2 1 timezone=America/New_York`. Raw `alertExpr` still works. `get_datasource` and `get_resource_group_datasource_thresholds` add `alertExprParsed` for windowed thresholds. The `lm://knowledge/alert-thresholds` resource documents the syntax.

- Alert trigger and clear intervals are now explained as poll cycles. `alertTransitionInterval` and `alertClearTransitionInterval` count cycles after the first poll: 0 = alert at the first violating poll, N = N+1 consecutive polls spanning N x the collection interval (at a 5-minute poll: trigger 1 = 2 polls = 5 minutes, clear 12 = 60 minutes). `create_datasource`, `update_datasource`, `get_datasource`, `update_resource_group_datasource_thresholds` and `get_resource_group_datasource_thresholds` state the rule; `get_datasource` and `get_resource_group_datasource_thresholds` add `alertIntervals` to each datapoint (polls and minutes for that DataSource); and the create/update tools return a `warning` (they still write) when a `> 0` threshold has a trigger interval above 0, because a one-poll spike will not alert. New knowledge resource `lm://knowledge/alert-thresholds` with the formula and examples.
- Widget columns without hand-written JSON. `create_widget` for an alert list now starts from the UI's standard column list (LogicMonitor creates it with none) and takes `columns` (the same changes as `update_widget`, including `##property##` custom columns). `update_widget` takes `tableColumns` for dynamic tables: add or remove an instance property column (`{instanceProperty:"auto.lm.token.owner"}`), change a datapoint column's `colorThresholds`, `displayType`, range or size, and add or remove datapoint columns, with `columns`, `columnsV4`, `displaySettings.columns` and `instanceColumns` kept in step as the UI writes them. The tool descriptions and the `dashboards-and-widgets` knowledge resource now say that a row label does not resolve property tokens and that `get_widget_data` does not return property columns.
- Output size caps. `test_datasource` is compact by default: the first `maxInstances` (default 5) instances in full, `instancesWithMissingValues` naming any other instance with a datapoint that had no value, and each script's raw output cut to 2,000 characters, with `truncated` and `truncationNote` saying what was left out (a 46-instance DataSource was about 230,000 characters); `verbose: true` returns everything as before. `get_widget_data` cuts the widget's largest list (table rows, series points) to what fits in about 40,000 characters, with a note giving the total; `maxRows` sets an exact count instead. `get_datasource`, `get_widget` and `list_dashboards` accept dot paths in `fields` (for example `dataPoints.id,dataPoints.name`), which LogicMonitor itself answers with `{}`. `list_users` returns each role as `{id, name}` instead of the full privilege list.
- `test_datasource` now reads `id.datapoint: value` lines as well as `id.datapoint=value` (the collector accepts both), so datapoints no longer show a false "no data" note. `discovery` and `collection` carry `exitCode` and any `error` text, and `warnings` says explicitly when a script printed nothing (the collector returns no stderr). `schedule_resource_discovery` now returns `{scheduled, deviceId, scheduledAt, response, hint}` pointing to `list_resource_instances` instead of `{}`.
- New `set_resource_property_bulk`: set one custom property to one value on many resources (`deviceIds`, or a `filter`; up to 100). It defaults to a dry run that returns `{deviceId, displayName, oldValue, newValue, status}` per resource without writing (statuses `would-create`, `would-update`, `unchanged`); pass `dryRun: false` to write. Failures are reported per resource and do not stop the rest. Hidden on read-only portals like the other write tools.
- New knowledge resource `lm://knowledge/dynamic-groups-and-auto-properties`: how dynamic (`appliesTo`) groups work, custom vs system vs auto properties, why a resource stays in its old group after you edit a property an auto property is copied from (the PropertySource has to rerun first), a verify-after-change order (custom property, auto property, group membership) using `list_resource_properties` and `get_resource_group_membership`, and how to nudge a refresh with `schedule_resource_discovery`.
- New `get_resource_group_membership` (which groups is this resource in, and why): each direct group with name, full path, whether it is dynamic and, for dynamic groups, the `appliesTo` rule plus the values of the resource's own properties that rule names. New `find_resource_groups_by_applies_to` (the reverse): groups whose `appliesTo` contains some text, such as a property name or a sysid.
- `list_resources` and `get_resource` take `expandGroups`: each resource gets a `groups` array of `{id, name, fullPath, appliesTo}` resolved from its `hostGroupIds` (appliesTo only for dynamic groups), so "which groups is this device in, and why?" needs no per-id `get_resource_group` calls. Lookups are cached per call.
- The `lm://knowledge/dashboards-and-widgets` resource explains how to colour a whole dynamic table cell by state: a `colorBar` column with `minValue:-1`, `maxValue:0` and `colorThresholds` (level 2 yellow, 3 orange, 4 red, green below every threshold) fills the cell instead of showing a progress bar, how `get_widget_data` reports it, and that LogicMonitor allows only two such columns per table. The same resource now also covers the 10-column table limit, that a table column's `rpn` only sees its own datapoint (no virtual datapoints, so a derived value must be a datapoint of the DataSource), and the gauge widget (a "% of portals" figure from an `AVERAGE` aggregate times 100, and that the denominator is the instances that report).
- Resource tools accept `resourceId` (and `resourceIds`) as an alias for `deviceId` (`deviceIds`); the device names stay canonical and win if both are given.
- Portal rate limit is now configurable (`MCP_RATE_LIMIT_MAX`, `MCP_RATE_LIMIT_WINDOW_SECONDS`, `MCP_AUTH_RATE_LIMIT_MAX`) and visible: `/health` reports the limit and the busiest client's usage and reset time, the 429 body says it is the MCP server's limit (not LogicMonitor's) with limit, window and retry time, and `/health`/`/healthz` no longer count against it. Portal Manager: `edit-portal.sh --rate-limit-max/--rate-limit-window` and a Rate limit column in the web UI.

### Fixed
- `list_collectors` and `get_collector` descriptions now match the API. `status` is the registration status (0 unregistered, 1 registered, 2 stopped, 3 suspended), not alive/dead, so the suggested `filter:"status:alive"` silently matched nothing; the up/down flag is `isDown` (`filter:"isDown:false"`). Removed the promised `lastHeartbeatTime`, free disk space and CPU/memory fields, which are not on the collector object (they come from the collector host's own DataSources, found through `collectorDeviceId`). `numberOfInstances` is now documented: it is only maintained for collectors in auto-balanced collector groups (0 elsewhere) and about one per host below the true count. `list_collectors` now returns `isDown`, `build`, `numberOfInstances`, `collectorGroupName` and `collectorDeviceId` by default (the description already promised the build version)
- Tool descriptions no longer point at tools that do not exist. 59 references to 31 names were stale: old `device` names (`list_device_instances`, `update_device_property`, `create_device_sdt`, ...), `search_*` names that are really `list_*` with a `query` argument, and tools that were never implemented (`create_user`, `update_user`, `create_api_token`, `generate_report`, `run_netscan`, `test_integration`, ...). References are corrected or removed, a 404 error suggestion no longer mentions `search_resources`, and `LOGICMONITOR-API-COVERAGE.md` no longer lists `search_resources`, `search_alerts` or `search_audit_logs`. A new test fails if any description names a tool that does not exist
- `get_resource_instance_data` no longer returns a misleading window when only one end of the time range is given. LogicMonitor answers a lone `start` with `start`..`start`+1h (not up to now, and without a truncation marker) and ignores a lone `end`. A lone `start` now ends at "now" and a lone `end` starts one hour earlier. The tool description also said the default window was the last 2 hours; it is about the last hour
- `get_widget_data` with a lone `start` now ends at "now" (LogicMonitor rejected it with HTTP 400 "Invalid time range"), and a lone `end` is rejected with a clear error instead of being silently ignored by LogicMonitor (which returned the widget's default window ending now)
- `update_resource_property` and `update_resource_group_property` can now add a property that doesn't exist yet. LogicMonitor's `PATCH .../properties/{name}` only updates existing properties (404 "Property(name=...) is not found"); on that specific 404 the tools now fall back to `POST .../properties`. Results include `action: "updated" | "created"`; other errors (including a missing device/group) are not retried. Tool descriptions now use the real `propertyName` parameter instead of `name`
- `create_datasource` now supports `hasMultiInstances` (create-only in LogicMonitor); previously it was silently dropped, producing unusable single-instance DataSources. Defaults to `true` when `enableAutoDiscovery` is `true`; an explicit `false` is respected
